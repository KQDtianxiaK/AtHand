# AtHand V3：从 AI 工作台到个人 AI 运营系统

## 文档目的

这份文档把两件事情合在一起回答：

1. AtHand 当前为什么会出现目标用户不清晰、产品定位模糊、自己也没有成为日常第一入口的问题。
2. 如果 AtHand 要继续走下去，V3 应该朝哪个方向收敛，以及基于现有仓库形态应该如何重组信息架构。

这不是功能清单，也不是 PRD。它是一次产品定义上的重置。

---

## 一、当前问题不是“功能还不够”，而是“方向开始互相冲突”

### 1. 当前仓库已经做成了什么

从当前仓库的事实看，AtHand 已经不只是一个想法，而是一套相当完整的系统：

- 根文档 [../README.md](../README.md) 把 AtHand 描述为“AI 原生远程工作台，用于 Agent 编排与个人执行流协作”。
- 子项目文档 [../athand-hub/README.md](../athand-hub/README.md) 把它定义为“个人全能远程工作台”。
- 前端导航 [../athand-hub/frontend/src/components/Sidebar.tsx](../athand-hub/frontend/src/components/Sidebar.tsx) 当前一级入口包括：AI 管控、待办、备忘录、打卡、邮箱、新闻。
- 后端入口 [../athand-hub/backend/main.py](../athand-hub/backend/main.py) 当前已经把 assistant、ai_control、email、news、stats、todos、memos、clock 作为并列业务域接入。
- 全局 AI 助手 [../athand-hub/frontend/src/components/AssistantPanel.tsx](../athand-hub/frontend/src/components/AssistantPanel.tsx) 已经具备跨模块对话、工具调用、确认动作的雏形。

问题在于：这些能力都真实存在，但它们还没有被一个足够锋利的产品主张统一起来。

### 2. 原始灵感与当前产品形态已经发生偏移

AtHand 的最初灵感明显来自 [../胡渊鸣-我给10个claude-code打工.md](../胡渊鸣-我给10个claude-code打工.md) 里那套工作方式：

- 人的想法会在任意时刻出现，需要低摩擦捕获。
- AI 要能持续接活、并行执行、不中断地跑。
- 用户需要一个地方去派发、观察、纠偏、续聊、确认和沉淀经验。
- 软件不再是“标准功能集合”，而是个人为自己搭出的高杠杆工作系统。

但当前 AtHand 的形态，已经逐渐偏向另一件事：

- 一套带 AI 能力的个人办公软件。

这两者不是完全矛盾，但它们的产品重心并不一样：

- 前者的核心是“任务编排、执行监督、上下文和授权边界”。
- 后者的核心是“模块完整度、页面覆盖率和功能齐全度”。

如果继续同时往这两边长，产品会越来越难讲清楚。

## 二、当前 AtHand 的四个核心问题

### 1. 目标用户定义过窄，而且不稳定

如果把 AtHand 理解为“给科技公司 CEO 的定制支持软件”，那它的问题很明显：

- 目标用户太小。
- 这类用户通常要么已经有专门团队、要么自己也有很强的定制能力。
- 这类用户的工作流差异极大，很难被一个标准产品自然覆盖。

更关键的是，这个定义无法解释为什么普通但高杠杆的个体用户也需要它。

AtHand 真正可能服务的，不是“CEO”这个职位，而是这样一类人：

- 同时管理多个 AI 会话和多个任务流的人。
- 需要在信息输入、行动派发、结果 review、不可逆动作审批之间快速切换的人。
- 已经在用 Claude Code、Codex、paseo、VS Code、浏览器工具，但缺少一个统一协调层的人。

这比“CEO 工具”更大，也更贴近 AtHand 已经做出来的东西。

### 2. 产品定位漂移成了三件事的混合体

当前 AtHand 实际上同时在尝试做三种产品：

- AI orchestration desk：管理会话、历史、timeline、继续对话、权限确认。
- 个人办公套件：待办、备忘录、打卡、邮箱、新闻、统计。
- AI 定制化平台：希望通过内嵌 AI 帮用户按需生成功能和工作流。

这三件事可以相互支撑，但不能在同一阶段同时都做主线。

它们分别对应三种完全不同的竞争场：

- 对 AI orchestration desk，竞品是 Claude Code、Codex、paseo、vibe-kanban 一类工具。
- 对个人办公套件，竞品是邮箱、日历、待办、知识库、阅读器等成熟软件。
- 对 AI 定制化平台，竞品是各种 AI builder、workflow builder、low-code agent systems。

如果不先选一个主轴，AtHand 会一直看起来“什么都能做一点”，但始终很难成为任何一种用户的第一入口。

### 3. 竞争判断容易落在错误的层面

AtHand 不应该主要和“邮箱软件”“新闻软件”“待办软件”比较。

对用户来说，真正的替代方案往往是：

- 继续直接在 VS Code、Claude Code、Codex、Kimi Code 里干活。
- 继续用现有软件，然后用聊天式 AI 做辅助。
- 用已有的 agent manager 或 workflow 工具拼一个自己的系统。

所以 AtHand 的问题不是“邮箱页是不是比别人的邮箱页更完整”，而是：

- 为什么用户要先打开 AtHand，而不是先打开 IDE、终端、Claude Code 或浏览器？

只要这个问题没有被回答，新增再多模块也只是让系统更厚，不会让它更有入口价值。

### 4. 自己没有形成第一入口，说明产品锚点还没建立

这是最重要的信号之一。

如果产品的主要构建者自己都没有形成“先打开它，再决定后续动作”的习惯，通常说明以下几件事至少有一件成立：

- 系统没有提供不可替代的组织能力。
- 主入口不够顺手，仍然比现有工作流多一层。
- 产品把太多精力放在“功能页面”上，而不是“任务流主循环”上。
- 用户最强烈的那条需求还没有被压到极致。

对 AtHand 来说，这意味着下一阶段不该继续平铺页面，而应该优先把“第一入口”做出来。

## 三、AI 时代产品最基本的设计理念应该是什么

如果把模型能力持续提升当作确定趋势，而不是可选前提，那么 AI 产品的设计理念应该和传统 SaaS 很不一样。

### 1. 默认假设：智能会越来越便宜，注意力不会

在 AI 时代，最稀缺的资源不会是生成能力，而会是：

- 用户的注意力。
- 用户愿意亲自拍板的时间。
- 用户能承受的上下文切换次数。
- 用户对风险动作的授权边界。

因此产品不该把重点放在“再给用户多一个生成按钮”，而应该放在：

- 如何减少用户必须亲自盯着看的东西。
- 如何只把真正值得用户决策的节点推到他面前。

### 2. 默认假设：AI 可以执行，但用户仍然负责目标与边界

当模型足够强以后，用户的价值不在于写每一步操作说明，而在于：

- 定义目标。
- 提供关键约束。
- 设定优先级。
- 对不可逆动作做最终确认。
- 在结果偏航时重新校准方向。

因此好的 AI 产品不是“替用户把每一步都藏起来”，而是：

- 帮用户把目标、约束、审批和反馈回路组织清楚。

### 3. 默认假设：并行智能越多，越需要统一操作平面

如果未来一个用户会同时调度多个 agent、多个模型、多个工具、多个外部系统，那么新的核心问题不是“单个 AI 能不能回答问题”，而是：

- 我现在到底在推进哪些目标？
- 哪些动作已经在执行？
- 哪些执行卡住了？
- 哪些结果要我 review？
- 哪些地方暴露了新的长期偏好和知识，需要沉淀下来？

这意味着未来的核心产品价值会集中到：

- 编排。
- 可观察性。
- 审批。
- 记忆。
- 权限与责任边界。

### 4. 默认假设：产品应该在“AGI 已足够强”时依然成立

如果未来模型真的接近通用 agent，AtHand 仍然需要回答：

- 为什么用户还需要我？

合理答案不应该是“因为我也能聊天”，而应该是：

- 因为我帮用户管理大量智能体和大量任务流。
- 因为我把授权、审批、历史、偏好、连接器、记忆和组织层固定下来。
- 因为我让智能体从“单次执行”变成“可持续运营”。

也就是说，AI 越强，AtHand 越不该做一个更大的聊天框，而应该做一个更强的操作台。

## 四、给 AtHand 的务实 AGI 定义

这里不讨论哲学意义上的 AGI，而给一个产品设计可用的定义。

如果一个模型满足以下条件，就足以把产品设计推进到“按 AGI 前提构想”的阶段：

- 能接收模糊目标并主动追问关键缺失信息。
- 能跨工具完成多步任务，而不是只在单一窗口内回答。
- 能自检、自修、解释失败和提出下一步。
- 在大多数办公、学习、知识工作场景下，端到端完成质量接近可靠的人类通才。
- 能在一段较长的任务链里持续保持状态和目标一致性。

如果以这个标准看，AtHand 不应该假设“AI 只是个功能点”，而应该假设：

- AI 很快会成为主执行体。
- 人会越来越像目标设定者、审批者和系统设计者。

这会直接改变产品形态。

## 五、AtHand V3 应该是什么

### 1. 一句话定位

AtHand V3 不应该继续定义为“带 AI 的个人办公工作台”，而应该定义为：

**面向高杠杆个体的个人 AI 运营系统。**

它的任务不是替代所有办公软件，而是把用户的目标、上下文、多个 agent、外部信息源、待审批动作和长期记忆组织到一个可持续运营的系统里。

### 2. 第一目标用户

AtHand V3 的第一目标用户建议收敛为：

- 技术型个体创业者。
- 高频使用 Claude Code、Codex、paseo、VS Code 的独立开发者或小团队负责人。
- 同时推进多个项目、多个信息流、多个 AI 会话的人。
- 对定制化系统有需求，但不想自己永远维护一堆零散脚本和窗口的人。

这类用户不一定是 CEO，但他们的共同点是：

- 已经有 AI 使用习惯。
- 已经在多工具之间来回切换。
- 对“统一协调层”有真实价值感知。

### 3. 非目标用户

AtHand V3 不应该优先服务以下人群：

- 只需要一个聊天机器人或一个普通效率工具的人。
- 不愿意给 AI 较高执行权限的人。
- 需要标准化企业 SaaS、强组织协作和复杂权限体系的大型团队。
- 希望 AtHand 直接替代成熟邮箱、日历、文档、IM、知识库全家桶的人。

这不是价值判断，而是聚焦判断。

### 4. 核心 Job To Be Done

AtHand V3 需要优先解决的，不是“我缺一个邮箱页”，而是这句话：

**当我同时有很多目标、很多信息源、很多 AI 在跑时，我需要一个地方来捕获、澄清、派发、观察、审批和沉淀。**

它的核心闭环应该是：

1. Capture：快速捕获想法、请求、邮件、链接、新闻、语音输入。
2. Clarify：AI 追问缺失信息，把模糊意图变成结构化任务。
3. Dispatch：把任务分配给一个或多个 agent、工具链或外部系统。
4. Observe：统一查看运行状态、timeline、卡点、失败原因。
5. Approve：把不可逆动作提请用户审核和确认。
6. Learn：把偏好、模板、失败经验和关键知识写回长期记忆。

只要一个功能不服务这个闭环，就不应占据一级战略位置。

## 六、AtHand V3 的护城河不应该建立在“功能页更多”上

如果未来 Codex、Claude Code、paseo 乃至更通用的 agent 都能直接接入各种办公和学习软件，AtHand 的优势不能建立在“我也有一个邮箱页”和“我也有一个新闻页”。

V3 的潜在护城河应该建立在下面这些层上：

- 持续的个人上下文与长期记忆。
- 统一的任务编排和多 agent 协调。
- 对不可逆动作的审批流和责任边界。
- 跨工具、跨信息源的状态可观察性。
- 用户可以用自然语言组装自己的工作系统，但运行在受约束、可维护的底座上。

换句话说，AtHand 不该卖“一个又一个模块”，而该卖“让用户持续运营自己工作系统的能力”。

## 七、基于现有仓库，V3 应该如何重组信息架构

### 1. 现有架构的问题在哪里

当前一级导航是按模块分类的：

- AI 管控
- 待办事项
- 备忘录
- 打卡
- 邮箱
- 新闻

这是一种典型的“应用抽屉式信息架构”。

它的问题是：

- 它默认用户先知道自己要进哪个模块。
- 它把“任务推进”切碎成多个页面。
- 它更像一个工具集合，而不是一个运营系统。
- 它会让 AI 助手看起来像“附加层”，而不是“主入口”。

V3 应该改成按任务流和运营流组织，而不是按应用分类组织。

### 2. 建议的新一级信息架构

建议 V3 的一级信息架构收敛成下面五个面：

| 一级入口 | 作用 | 说明 |
| --- | --- | --- |
| Today | 今日总览与优先级面板 | 只显示当前最值得看、最该拍板、最该推进的内容 |
| Inbox | 统一捕获入口 | 汇总用户输入、邮件摘要、新闻线索、AI 生成的新任务和待澄清需求 |
| Missions | 目标与工作流 | 把原来的待办提升成更高层的目标、计划、子任务、责任 agent |
| Runs | 执行与会话控制 | 承接当前 AI 管控看板、timeline、history、继续对话、权限请求 |
| Memory | 长期记忆与知识沉淀 | 包含备忘录、偏好、模板、规则、经验教训 |

除此以外，建议把下面这些从一级导航中降级：

- Email：降级为连接器和专用详情视图，不再作为主产品面。
- News：降级为信息源和摘要来源，不再作为主产品面。
- Clock：降级为 Today 内部的节奏与专注数据，不再单独承载主叙事。
- Settings/Connectors：单独放到次级区域，承载账号、连接器、模型、权限和系统配置。

### 3. 现有模块到 V3 的映射

| 当前模块 | 当前角色 | V3 角色 | 建议动作 |
| --- | --- | --- | --- |
| Dashboard | 总览页 | Today | 保留，但改成“待处理事项 + 运行状态 + 审批 + 今日重点”中心 |
| AI 管控 | 独立一级主场景 | Runs | 保留，并升级为 V3 核心执行面 |
| AssistantPanel | 全局附加面板 | 全局主入口 | 保留，并提升为主入口与统一 Composer |
| Todos | 独立任务页 | Missions 的子视图 | 保留数据模型，弱化为目标执行视图 |
| Memos | 独立知识页 | Memory | 保留，并扩大为偏好、模板、规则、经验库 |
| Clock | 独立工具页 | Today 的运营指标 | 降级合并 |
| Email | 独立工作区 | Inbox/Connectors/Approvals | 降级为输入源、动作目标和专用详情页 |
| News | 独立工作区 | Inbox/Connectors | 降级为输入源和摘要来源 |

### 4. 应该保留并强化的能力

从现有实现看，V3 最值得继续作为核心资产的不是页面数量，而是这些能力：

- [../athand-hub/backend/services/ai_control_bridge.py](../athand-hub/backend/services/ai_control_bridge.py) 对 paseo 的 bridge-first 接入。
- [../athand-hub/frontend/src/components/AiControlBridgePanel.tsx](../athand-hub/frontend/src/components/AiControlBridgePanel.tsx) 已经形成的会话看板、状态列、timeline 和续聊机制。
- [../athand-hub/backend/api/assistant.py](../athand-hub/backend/api/assistant.py) 里的工具调用、流式回复、确认动作约束。
- [../athand-hub/frontend/src/components/AssistantPanel.tsx](../athand-hub/frontend/src/components/AssistantPanel.tsx) 作为全局 sidecar 的入口形式。
- 邮件发送确认、权限确认这类 human-in-the-loop 机制。

这些是 AtHand 未来真正应该变强的部分，因为它们对应的是运营系统的中枢，而不是外围页面。

### 5. 应该降级为“连接器”和“派生视图”的能力

下列能力仍然重要，但不应该继续占据产品定义的中心：

- Email：更像输入源、动作目标、审批场景。
- News：更像信号源和摘要源。
- Clock：更像个人节奏数据。
- 纯 CRUD 型 Todos：更像 Missions 内部的一种结构。

它们仍然可以保留页面，但在叙事上必须服从主闭环，而不是与主闭环并列。

## 八、AtHand V3 不应该做成“AI 自由写全栈代码的平台”

你提出的方向里有一个很重要但也很危险的分支：

- 用户提出需求，AI 自己去找参考代码，然后开始构建新功能。

这个方向在理念上是对的，但不能直接等价于“让 AI 自由生成整套产品代码”。

因为一旦复杂度升高，就会出现：

- 生成成本高。
- 错误率高。
- 可维护性迅速变差。
- 系统开始变成“能做任何事，但没有稳定边界”的泥团。

V3 更合理的做法是：

- 不让 AI 随意生成整个系统。
- 而是让 AI 在受约束的底座上组装工作流、视图和自动化能力。

也就是说，AtHand 真正该产品化的应该是这些原语：

- 实体与字段。
- 列表、看板、时间线、详情面板。
- 任务状态与审批节点。
- 连接器与触发器。
- 摘要、回顾、日报。
- 偏好、模板、规则和记忆。
- agent 角色与执行策略。

用户未来应该对 AtHand 说：

- 帮我搭一个客户跟进工作流。
- 帮我搭一个论文阅读与批注流程。
- 帮我搭一个个人研究运营台。

而 AtHand 的正确响应不是“从零自由写一套应用”，而是：

- 先追问关键约束。
- 再在稳定原语上组合出结构化系统。

这样 AtHand 才会在模型变强时同步变强，而不是被更强的模型直接吞掉。

## 九、V3 的产品原则

如果用几条短句定义 AtHand V3，我建议是：

1. AI 是主执行体，人是目标定义者、审批者和系统校准者。
2. 智能不是稀缺资源，注意力和决策权才是。
3. 主入口必须是任务流，不是应用分类。
4. 不可逆动作必须显式确认。
5. 所有重要执行都必须可观察、可继续、可追溯。
6. 所有高频偏好都应该沉淀成长期记忆，而不是每次重新 prompt。
7. 用户应该能定制自己的系统，但要建立在受约束的底座上。

## 十、下一步不是“继续加页面”，而是收口

### 1. 立刻该停止的事情

在 V3 定义清楚之前，不建议继续做以下类型的扩张：

- 新增一个并列一级页面。
- 把邮箱、新闻、待办继续做成更完整的独立产品。
- 把“AI 会帮你定制功能”直接实现成自由写全栈代码能力。

### 2. 最应该优先做的三件事

#### 第一件：确定唯一主入口

需要把“我先打开什么”这个问题做出明确答案。

建议答案是：

- Assistant + Today 组合成为统一入口。

用户先进入 Today，看当前目标、待审批、进行中执行和新信号；任何新需求都先从 Assistant/Inbox 进入，而不是先跳去某个模块页。

#### 第二件：统一核心对象模型

V3 需要一套比“todo、memo、email、news、session”更高层的对象模型。建议至少形成这几个核心对象：

- Mission：一个阶段性目标或主题任务。
- Run：一次由 AI 或工具链发起的执行。
- Artifact：执行产生的文稿、摘要、回复草稿、计划、结论。
- Approval：需要用户拍板的动作。
- Memory Entry：沉淀下来的长期偏好、规则、模板、经验。

有了这套对象，现有页面才有可能被重新组织成一个系统，而不是一堆模块。

#### 第三件：把 Email、News、Todos 重新定义为“服务主循环”

不是删除它们，而是改变它们在系统中的身份：

- Email 和 News 主要负责喂给 Inbox 新信号。
- Todos 主要服务 Missions 的拆解和推进。
- Clock 主要服务 Today 的节奏反馈。
- Memos 主要服务 Memory 的长期沉淀。

这样系统的重心才会重新回到：

- 任务流、执行流、审批流、记忆流。

## 十一、建议的 V3 迭代顺序

### Phase 0：战略收口

- 冻结新的独立功能页开发。
- 统一对外定义：AtHand V3 是个人 AI 运营系统，而不是全能办公套件。
- 明确首批用户：高频使用 AI 工具的高杠杆个体。

### Phase 1：第一入口改造

- 把 Today 做成真正的“今日运营台”。
- 把 Assistant 从附加面板提升为主入口和统一 Composer。
- 新增 Inbox/Approvals 视图，把邮件、新闻、AI 生成的待确认事项统一汇入。

### Phase 2：核心对象收敛

- 重新定义 Mission、Run、Artifact、Approval、Memory Entry。
- 把现有 Todo、Session、Memo、Email Draft 等数据结构往这套对象体系映射。

### Phase 3：模块降级与重组

- 把 Email、News、Clock 从一级导航降级。
- 把 Todos 并入 Missions。
- 把 Memos 升级为 Memory。
- 保持 Runs 作为核心执行面。

### Phase 4：受约束的“按需构建”能力

- 不直接让 AI 自由生成整站代码。
- 先做在受约束原语上的工作流搭建、字段设计、列表/看板/审批流编排。

## 十二、判断 V3 是否走对的三个标准

### 1. 你自己是否开始先打开 AtHand

如果未来两周内，自己的新任务、新想法、新输入，第一步仍然不是进入 AtHand，那么说明主入口仍然不成立。

### 2. 用户是否能一句话理解产品

如果用户还需要听完“它也有邮箱、也有新闻、也有待办、也能管 AI”才能大致理解 AtHand，那定位仍然太散。

正确状态应该是：

- “它是我管理 AI 工作流、审批和长期记忆的个人操作台。”

### 3. 新功能是否都能映射回主闭环

以后每加一个功能，都应该先问：

- 它是在增强 Capture、Clarify、Dispatch、Observe、Approve、Learn 的哪一段？

如果回答不上来，就不该优先做。

## 十三、最终结论

AtHand 的问题不是做得太少，而是已经走到了一个必须重新收束定义的节点。

最合理的下一步，不是继续把它做成更完整的办公软件，也不是直接把它做成一个“AI 任意生成软件”的平台，而是把它重定义为：

**一个帮助高杠杆个体运营自己 AI 工作系统的个人操作台。**

在这个定义下：

- AI 管控不是附属功能，而是核心执行面。
- Assistant 不是边栏配件，而是主入口。
- Email、News、Todos、Clock 不再是并列产品，而是输入源、派生视图、审批场景和运营数据。
- Memory 不只是备忘录，而是整个系统持续变聪明的基础。

如果 V3 能按这个方向收口，AtHand 才有机会从“做了很多模块的工作台”，变成“一个真正能承载 AI 时代个人工作系统的产品”。
